초과 판매 건수는 실행마다 달라지지만 락을 건 방식은 매번 0건이었습니다. 소요 시간은 단일 측정이라 속도 비교에는 쓰지 않습니다.

무슨 일이 일어났나

  • 락 없음 — 여러 요청이 같은 재고 값을 동시에 읽고 각자 차감해 덮어써서(lost update), 재고 카운터는 0인데 예매 기록은 재고의 8~10배가 쌓였습니다.
  • 비관적 락 — SELECT ... FOR UPDATE로 회차 행을 잠가 요청을 한 줄로 세웠습니다. 정합성은 확실하지만 같은 회차 요청이 대기합니다.
  • 낙관적 락 — 잠그지 않고 읽은 뒤 version이 그대로일 때만 차감하고, 충돌하면 재시도합니다. 1,000건 중 410번 충돌해 재시도했습니다.

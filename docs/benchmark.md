# 락 방식별 벤치마크

시나리오: 재고 100, 동시 요청 1,000 (스레드 64개)

## 1. 정합성 (JUnit `ReservationConcurrencyTest`, H2 인메모리, 2026-10-28)

H2 기준 참고 수치다. 최종 수치는 MySQL + k6 로 다시 측정해 아래 2번 표를 채운다.

| 방식 | 성공 응답 | 확정 예매 | 남은 재고 | 초과 판매 | 소요(ms) |
|---|---|---|---|---|---|
| 락 없음 | 986 | 986 | 0 | **886건** | 386 |
| 비관적 락 | 100 | 100 | 0 | **0건** | 640 |
| 낙관적 락 (CAS + 재시도) | 100 | 100 | 0 | **0건** | 652 (재시도 410회) |

추가 실행 기록(락 없음 초과 판매): 800건(성공 응답 900), 900건(성공 응답 1,000 · 남은 재고 카운터 3). 같은 조건에서 낙관적 락 재시도는 363회, 361회였다.

재실행(같은 조건) 참고: 락 없음 초과 판매 765건 / 비관적 락 0건(478ms) / 낙관적 락 0건(652ms, 재시도 410회). 초과 판매 건수는 실행마다 달라지지만 락 방식은 매번 0건이었다.

- 락 없음: 여러 스레드가 같은 재고 값을 읽고 각자 차감해 덮어써서(lost update), 재고 카운터는 0인데 예매 기록은 986건이 쌓였다.
- 비관적 락: `SELECT ... FOR UPDATE` 로 회차 행을 직렬화해 정확히 100건만 판매됐다.
- 낙관적 락: 읽은 version 이 그대로일 때만 차감(조건부 UPDATE)하고, 충돌하면 재시도한다. 요청 1,000건 중 충돌로 인한 재시도가 410회 발생해 충돌 비용이 눈에 보인다. 비관적 락은 대기만 하고 재시도는 없다.
- 소요 시간은 실행 순서(JIT 워밍업)에 영향을 받는 단일 측정이라 방식 간 속도 비교로 쓰지 않는다.

## 1-2. 정합성 (웹 화면 `동시성 시연`, Oracle 19c, 2026-10-28)

같은 시나리오(재고 100, 동시 요청 1,000, 스레드 64개)를 실제 DB(Oracle 19c)에서 1회 실행한 결과.

| 방식 | 성공 응답 | 확정 예매 | 초과 판매 | 재시도 | 소요(ms) |
|---|---|---|---|---|---|
| 락 없음 | 743 | 743 | **643건** | - | 508 |
| 비관적 락 | 100 | 100 | **0건** | - | 756 |
| 낙관적 락 | 100 | 100 | **0건** | 851회 | 505 |

- H2와 같은 경향이다: 락 없음은 초과 판매가 발생하고, 락을 건 두 방식은 정확히 재고만큼만 판매된다.
- 낙관적 락의 재시도는 H2에서 360~410회였는데 Oracle에서는 851회로 늘었다. DB가 달라지면 충돌 비용도 달라진다.
- 소요 시간은 단일 측정이라 방식 간 속도 비교로 쓰지 않는다.

## 2. 부하 테스트 (k6 `k6/reserve.js`, Oracle 19c, 2026-10-28)

조건: 재고 100, 동시 요청 1,000(VU 1,000 × 1회), 앱과 DB와 k6가 모두 같은 PC에서 실행. 실패율은 재고 소진(409)을 정상으로 보고 그 외 오류만 센 값.
TPS = 요청 수 ÷ (첫 요청 ~ 마지막 응답) 시간. 방식마다 앱을 새로 띄워 측정(워밍업 후 값이 아니라 첫 측정 포함).

| 방식 | TPS | p95 (ms) | 실패율 | 최종 예매 건수 | 초과 판매 |
|---|---|---|---|---|---|
| 락 없음 | 681.2 | 695.7 | 0.00% | 347 | **247건** |
| 비관적 락 | 723.1 | 536.3 | 0.00% | 100 | 0건 |
| 낙관적 락 | 828.5 | 888.8 | 0.00% | 100 | 0건 |

- 비교 요약: 두 락 방식 모두 정확히 100건만 팔렸다. 낙관적 락은 TPS와 중앙값(106.3ms)이 비관적 락(183.1ms)보다 좋았지만, 충돌 재시도의 영향으로 꼬리 지연(p95 888.8ms, 비관적 락은 536.3ms)은 더 컸다.
- 이 차이는 각 방식 한 번씩(워밍업 후 두 번째 값)만 잰 값이고, 앱·DB·k6가 한 PC에서 돌아 서로 영향을 주므로 "어느 쪽이 항상 빠르다"는 결론으로 쓰지 않는다. 여러 번 반복해 평균을 내는 것이 다음 할 일이다.

- 비관적 락은 앱을 새로 띄운 직후의 첫 측정에서 예상 밖 오류가 8건(0.80%) 나왔다(TPS 776.4, p95 699.6ms). 오류 내용을 확인하지 못했고, 바로 이어서 한 번 더 측정한 위 값에서는 재현되지 않았다. 워밍업이 끝난 두 번째 측정 값을 표에 쓴다.
- 락 없음도 앱을 새로 띄운 뒤 두 번째 측정 값을 쓴다. 첫 측정은 초과 판매 153건(확정 예매 253), TPS 686.3, p95 997.3ms였고, 두 번째는 247건, TPS 681.2, p95 695.7ms였다. 초과 판매 건수는 측정마다 달라진다.
- 락 없음은 실패율 0.00%인데도 초과 판매가 발생한다. 모든 요청이 정상 응답을 받았지만 데이터가 틀린 것이다.

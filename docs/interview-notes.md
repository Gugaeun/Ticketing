# 면접 설명 정리

프로젝트를 **자기 말로 설명하기 위한 노트**입니다. 코드를 외우는 게 아니라, 아래 질문에 "왜"까지 답할 수 있으면 됩니다.
숫자는 `docs/benchmark.md` 기준이며, 반복 측정을 하면 그 값으로 바꿔서 말합니다.

## 0. 30초 소개

> 인기 공연 티켓 오픈 때 수천 명이 몰려도 초과 판매가 없는 예매 서비스를 만들었습니다.
> 재고 차감을 락 없이 구현해 **초과 판매를 먼저 재현**하고, 비관적 락과 낙관적 락으로 해결한 뒤 같은 시나리오로 비교했습니다.
> 재고 100장에 1,000명이 동시에 요청했을 때 락 없음은 247건이 더 팔렸고, 두 락 방식은 정확히 100건만 팔렸습니다.
> H2와 Oracle 19c에서 모두 확인했고, k6로 HTTP 부하 상태에서의 TPS와 응답시간도 측정했습니다.

## 1. 왜 락 없이 구현하면 초과 판매가 나나요?

- 재고 차감이 "읽기 → 비교 → 감소 → 저장" 여러 단계라서, 여러 요청이 **같은 재고 값을 동시에 읽고** 각자 차감해 덮어씁니다(lost update).
- 예를 들어 재고 1장일 때 두 요청이 둘 다 "1장 있음"을 읽으면 둘 다 성공하고, 저장되는 값은 0입니다.
- 결과적으로 **재고 카운터와 예매 기록이 어긋납니다.** 테스트에서 1,000건 전부 성공했는데 남은 재고 카운터는 3이었던 경우도 있었습니다.
- 가장 위험한 점은 **에러가 나지 않는다는 것**입니다. k6에서 실패율이 0.00%인데도 초과 판매가 발생했습니다. 오류 로그나 실패율만 보는 모니터링으로는 잡히지 않아서, 데이터 정합성을 직접 검증하는 테스트가 필요했습니다.

## 2. 비관적 락은 어떻게 해결하나요?

- 회차 행을 `SELECT ... FOR UPDATE`(JPA `PESSIMISTIC_WRITE`)로 읽습니다. 먼저 잡은 트랜잭션이 끝날 때까지 **다른 요청은 그 행에서 대기**합니다. 재고 차감이 한 줄로 직렬화됩니다.
- 장점: 정합성이 단순하고 확실합니다. 충돌이 잦은 상황(티켓 오픈)에 어울립니다.
- 단점: 대기 중인 요청이 DB 커넥션을 붙잡고 있어 **커넥션 풀이 고갈될 수 있고**, 트랜잭션이 길수록 대기가 길어집니다. 락을 여러 행에 거는 구조라면 데드락도 주의해야 합니다(이 프로젝트는 한 행만 잠가서 위험이 낮습니다).
- 락 안에서는 재고 확인, 차감, 예매 기록 저장만 하고 **트랜잭션을 짧게** 유지했습니다.

## 3. 낙관적 락은 어떻게 해결하나요?

- 잠그지 않고 읽은 뒤, 차감할 때 `UPDATE ... WHERE id = ? AND version = ? AND remaining_stock >= ?`로 **읽은 시점의 version이 그대로일 때만** 갱신합니다(CAS).
- 갱신된 행이 0건이면 그사이 다른 요청이 먼저 바꾼 것이니 충돌로 보고, 짧게 쉬었다가(1~5ms 랜덤) **재시도**합니다. 최대 100회를 넘으면 409로 응답합니다.
- 장점: 충돌이 적으면 락 대기가 없어서 빠릅니다. 커넥션을 오래 잡지 않습니다.
- 단점: **충돌이 많으면 재시도가 폭증**합니다. 실제로 요청 1,000건에서 재시도가 H2는 약 360~410회, Oracle은 851회까지 나왔습니다. 재시도는 일부 요청의 지연(p95)을 키웁니다.
- JPA `@Version`을 쓰지 않은 이유: 붙이면 "락 없음" 비교 구현도 함께 보호되어 초과 판매를 재현할 수 없습니다. 같은 원리를 조건부 UPDATE로 직접 구현해 **비교 기준(락 없음)을 유지**했습니다.

## 4. 측정 결과는 어떻게 해석하나요? (k6, Oracle 19c, 재고 100 / 요청 1,000)

| 방식 | 초과 판매 | TPS | 중앙값 | p95 |
|---|---|---|---|---|
| 락 없음 | 247건 | 681.2 | 188.3ms | 695.7ms |
| 비관적 락 | 0건 | 723.1 | 183.1ms | 536.3ms |
| 낙관적 락 | 0건 | 828.5 | 106.3ms | 888.8ms |

- 핵심은 **정합성**입니다. 두 락 방식은 매번 정확히 재고만큼만 팔았습니다.
- 낙관적 락은 중앙값과 TPS가 좋았지만 p95가 더 컸습니다. 충돌한 요청이 재시도를 반복하며 꼬리 지연이 길어진 것으로 해석합니다. (측정으로 확인한 것은 숫자뿐이고, 원인은 해석입니다.)
- **한계를 먼저 말합니다:** 방식당 한 번씩 쟀고, 앱·DB·k6가 한 PC에서 자원을 나눠 썼습니다. 그래서 "어느 쪽이 항상 빠르다"가 아니라 "정합성은 확보했고, 속도 차이는 반복 측정이 필요하다"고 말합니다. (반복 측정 후에는 평균과 표준편차로 바꿔 말합니다.)
- 락 없음의 초과 판매 건수는 측정할 때마다 달랐습니다(153, 247, 765~900건 등). 측정 방식(앱 내부 호출 vs HTTP)에 따라 충돌이 일어나는 정도가 달라지기 때문입니다.

## 5. 중복 예매는 어떻게 막나요?

- DB의 `unique(member_id, schedule_id)` 제약입니다. 애플리케이션에서 먼저 조회해서 확인하는 방식은 동시 요청에서 뚫리기 때문에, **최종 방어선을 DB 제약**으로 두었습니다.
- 제약 위반(`DataIntegrityViolationException`)은 409로 변환하고, 트랜잭션이 롤백되어 그 요청의 재고 차감도 취소됩니다.

## 6. 예매 완료 알림은 왜 비동기인가요?

- 예매 응답이 알림 처리(저장, 발송)에 묶여 느려지거나 실패하지 않도록, 예매가 성공한 뒤 **이벤트를 발행**하고 별도 스레드풀(`@Async`)에서 처리합니다.
- 알림 처리가 실패해도 예매에는 영향이 없습니다(예외를 잡아 로그만 남김). 발송부는 `NotificationSender` 인터페이스라 이메일이나 메시지 큐로 바꿀 수 있습니다.
- **한계도 말합니다:** 메모리 큐 기반이라 서버가 그 순간 죽으면 알림이 유실될 수 있습니다. 보장하려면 아웃박스 패턴이나 Kafka 같은 메시지 브로커가 필요합니다.

## 7. 인증과 권한은 어떻게 동작하나요?

- 로그인하면 JWT(회원 id, 역할 포함, 60분 유효)를 발급하고, 필터가 `Authorization: Bearer` 토큰을 검증해 회원 id를 principal로 넣습니다. 세션을 쓰지 않는 stateless 구조입니다.
- `/api/admin/**`는 `ADMIN` 역할만 접근할 수 있고, 인증이 없으면 401, 권한이 없으면 403입니다. 비밀번호는 BCrypt로 해시해 저장합니다.
- 한계: 리프레시 토큰과 토큰 폐기(로그아웃 시 무효화)는 구현하지 않았습니다.

## 8. 조회 최적화는 무엇을 했나요? ([`query-optimization.md`](query-optimization.md))

- 공연 목록 화면이 공연마다 상세 API를 따로 부르던 **N+1**을, 회차를 `IN` 조건 한 번으로 가져오는 API로 바꿨습니다.
- 오라클은 외래키에 인덱스를 자동으로 만들지 않아서 `(performance_id, start_at)`, 회차별 집계용 `(schedule_id, status)` 인덱스를 추가했습니다.
- `LIKE '%키워드%'` 검색은 일반 인덱스를 쓸 수 없어서 **하지 않은 이유**도 문서에 적었습니다.
- **측정:** 공연 11개 기준 SQL 실행 횟수가 23회에서 2회로 줄었습니다. 공연이 N개면 개선 전은 `1 + 2N`회, 개선 후는 N과 무관하게 최대 3회입니다. 화면의 HTTP 요청도 `1 + N`회에서 1회가 됐습니다.
- 인덱스의 실행 계획 비교(오라클, 예매 20만 건)는 아직 측정 전이라, 측정하기 전에는 "효과가 있을 것으로 예상한다"까지만 말합니다.

## 9. 왜 H2와 Oracle 둘 다에서 측정했나요?

- H2는 설치 없이 돌아가서 테스트와 개발에 쓰고, **실제 DB에서도 같은 결과가 나오는지**를 Oracle 19c로 확인했습니다. 락의 동작은 DB 구현에 따라 달라질 수 있기 때문입니다.
- 실제로 낙관적 락의 재시도 횟수가 DB에 따라 달랐습니다(H2 약 360~410회, Oracle 851회).
- 작업 PC에서 Docker 설치가 막혀 있어서 MySQL 대신 이미 설치된 Oracle을 썼고, 코드는 DB에 중립적으로 작성했습니다(DB 전용 타입 회피 등).

## 10. 더 개선한다면? (한계와 다음 단계)

- **Redis**: 재고를 Redis에서 원자 연산(`DECR` 또는 Lua 스크립트)으로 차감하면 DB 락 경합 없이 훨씬 높은 처리량을 낼 수 있습니다. 대신 Redis와 DB의 정합성(반영 시점, 장애 시 보정)이 새 문제가 됩니다. 구현하지는 않았고 설계만 정리했습니다.
- **대기열**: 티켓 오픈 순간 접속자를 순번으로 줄 세워 서버로 들어오는 요청 자체를 조절합니다.
- **측정 개선**: 앱·DB·부하 도구를 분리하고, 반복 측정으로 평균과 편차를 보고합니다.
- **배포는 하지 않았습니다.** 이 프로젝트의 목적이 동시성 문제의 재현과 방식별 비교라서 로컬에서 재현 가능한 실행 방법과 측정 기록으로 대신했습니다.

## 11. 예상 질문 한 줄 답변

| 질문 | 답 |
|---|---|
| 락 없이는 왜 틀리나? | 같은 재고 값을 동시에 읽고 각자 쓰는 lost update. 에러도 안 남. |
| 비관적 vs 낙관적? | 충돌이 많으면 비관적(대기), 적으면 낙관적(재시도). 티켓 오픈처럼 몰리면 낙관적은 재시도가 폭증. |
| 왜 `@Version` 안 썼나? | 락 없음 기준 구현까지 보호돼서 문제를 재현할 수 없어서. 조건부 UPDATE로 같은 원리 구현. |
| 데드락은? | 한 행만 잠가서 위험이 낮음. 여러 행을 잠그면 락 순서를 고정해야 함. |
| 중복 예매는? | DB unique 제약이 최종 방어선. 위반은 409로 변환. |
| 알림이 유실되면? | 메모리 큐라 가능. 아웃박스 패턴이나 브로커로 보완. |
| 측정이 신뢰할 만한가? | 한 PC에서 방식당 소수 회 측정이라 정합성은 확실하지만 속도 우열은 단정 못 함. 반복 측정으로 보완. |
| 이 코드를 직접 썼나? | AI의 도움을 받아 만들었고, 설계 결정(방식 선택, `@Version` 대신 CAS, 측정 방법)과 결과 해석은 직접 이해하고 설명할 수 있어야 함. |
